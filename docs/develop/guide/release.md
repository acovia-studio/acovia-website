# 发布与版本

数据包按服务器版本发布，标签形如 `v26.3-1`。发布内容包括数据包、更新日志与必要的文档修改。发布前应完成测试与备份。

## 版本号

- 主版本与服务器版本对应，例如 26.3。
- 同一主版本内的修订使用递增序号，例如 `v26.3-1`、`v26.3-2`。
- `pack.mcmeta` 的 `pack_format` 应与目标 Minecraft 版本一致；当前为 121。

## 发布前检查

1. 在测试存档中完成[本地开发与调试](/develop/guide/dev)中的检查表。
2. 确认 `pack.mcmeta`、维度、附魔、配方与函数无遗留调试代码。
3. 更新 `docs/server/changelog.md`，记录玩家可见的变化。
4. 更新开发文档中受影响的页面：维度、函数、附魔、物品、进度或世界生成。
5. 按[备份](/develop/maintain/backup)完成生产存档备份。
6. 在副本上验证升级流程；不得直接在生产存档上试验。

## 打包

数据包 ZIP 的根目录应直接包含：

```text
pack.mcmeta
data/
```

不得包含外层目录。打包后可在测试服务端执行 `/datapack list` 验证。

## 部署

1. 停止服务器。
2. 替换 `world/datapacks/` 中的数据包目录或 ZIP。
3. 启动服务器，检查启动日志中的数据包加载与维度注册。
4. 执行 `/datapack list` 与 `/function acovia:load` 验证加载。
5. 进入各维度，验证边界、传送、商店、物品与附魔。
6. 观察服务端日志，确认无函数报错或计划任务异常。

修改函数、配方、附魔与进度可通过 `/reload` 生效；新增维度或修改世界生成需要重启，并只影响新生成的区块。

## 回滚

1. 停止服务器。
2. 恢复上一版数据包。
3. 若本次发布修改了存档数据或世界生成，按[备份](/develop/maintain/backup)恢复对应存档。
4. 启动服务器，验证加载与关键功能。

数据包回滚不会撤销已经写入存档的区块、玩家数据或进度；涉及存档结构变更时，必须同时恢复备份。

## 标签与记录

发布完成后创建 Git 标签，标签名与发布版本一致。更新日志应记录版本号、日期、玩家可见变化与必要的迁移说明。开发文档中与本次发布相关的页面应在同一提交中更新。
